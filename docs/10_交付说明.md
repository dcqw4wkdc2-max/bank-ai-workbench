# 做到什么地步 + 怎么交付（D5 口径）

依据：《微光-银行客服 AI 工作台-任务书》11.1 统一交付物、12.2 D5、13.1 关键放行条件
结论先行：**做到"能被别人接手跑一遍"，就够交付了。** 不需要做成产品。

---

## 一、三条尺子量"到位没"

**功能尺（一条线走通就算过）**
咨询录入 → 内网取数 → 脱敏 → 出域 → 模型 → 规则裁决 → 人工确认 → 复原 → 审计。
四类意图（争议咨询 / 交易查询 / 疑似未授权 / 意图不明）都有明确走向；高风险一律转人工。

**证据尺（六样齐就算过）**
可运行原型、代码仓库、接口说明、测试报告、演示脚本、换人接手记录。

**安全尺（13.1 五类关键缺陷为 0 就算过）**
原始客户信息出域、MCP 越权、跨会话恢复、外网直连内网库、未审批改规则。

> 任务书原话：「评价同时看功能、业务正确性、安全、可维护性、换人接手和团队协作，不以代码量或演示效果单独排名。」

## 二、明确不做的六件事（做了也不加分，只消耗时间）

`① 真接银行核心系统 / 真实客户数据——PoC 阶段明确禁止`
`② 完整 RBAC 权限体系——现有角色隔离（坐席/管理/开发）够用`
`③ 性能压测与并发优化——没有真实负载，做了也没有结论`
`④ UI 精修、动画、暗黑模式——不影响验收`
`⑤ 多模型评测（R08 扩展卡）——可选，本轮不做`
`⑥ 新功能——周四前一律不加，只修缺陷`

## 三、现在到哪一档（自评）

`功能：D3 水平，已达到——12 例可跑，A/B/C 三类走向清楚，高风险 4/4 转人工`
`证据：约 20%——测试报告已有，缺代码仓库、接口说明、演示脚本成品、换人签收`
`安全：1 项未过——客户通道令牌未复原（P0-01）；MCP 那一项因页面挂死无法取证（P1-08）`

结论：**功能不缺，缺证据和两条 P0。**

## 四、怎么交付（三个动作，按顺序）

**动作一：交包（明天 21:00，交给苏鸿）**
一个 zip + 一个链接 + 一段录屏。包里六样：原型链接、仓库地址、接口说明、测试报告 v1.1、演示脚本、换人签收单。
交付方式：飞书/微信发 zip + 正文写三段话（这是什么、能演哪四段、代码在哪）。

**动作二：交现场（周四 18:30，苏鸿用）**
只演四条线、共 2 分 40 秒（05_演示脚本_四条线.md）：客户提交 → 低风险给建议 → 高风险转人工 → 故障回退。
现场只用冻结版；本地录屏一份、U 盘＋手机各存一份；演示归到苏鸿的"AI 安全"板块讲。

**动作三：交接手（明天 18:00 前）**
唐丽雯之外再找一个人（张心瑜或韦姿如），只按 README 独立启动一次，签收单上签字。
签收不了，说明这套东西还是"梁晓志的"，不是"第4组的"。

## 五、"交成功"的定义（三问，缺一不算交）

`① 苏鸿自己能不能点开、能不能讲？（链接＋脚本＋话术）`
`② 别人能不能只按文档跑起来？（README＋签收单）`
`③ 出事能不能查？（审计＋错误卡＋台账）`
