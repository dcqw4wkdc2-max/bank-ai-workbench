## 1. 模型异常不降级（关键项，10 行内）

**现状**：上游超时后工单永久停在 `AI_ANSWERING`，客户拿不到任何反馈。

**原实现位置**：`inner/agent.pyc` → `ModelConnector.invoke_local` / `_hermes_completion` / `_mock_completion`
（字节码里的 Docstring：「MODEL_IMPL=real 走牛马仕算力，失败降级 Mock（fail-closed）」「输出过不了 schema 校验就抛错降级」——降级是有的，但**没有回写到工单状态**）

**改成什么**：
- 捕获超时 → 工单 `status=TIMEOUT`，生成错误卡 `{code:"EC-TIMEOUT"}`，`decision=HUMAN_HANDOFF`
- 捕获非法 JSON / schema 失败 → `status=REJECTED`，错误卡 `{code:"EC-BADJSON"}`，不进入自动回复
- 两者都要写一条审计事件 `ERROR_CARD_ISSUED`

**参考实现**：`v2重写版/app.py` 的 `adjudicate()` 里 `fault` 分支 + `model_client.py` 的 `ModelTimeout` / `ModelSchemaError`

**验收**：`python tools/run_cases.py --base <你的端口>` → C03 应 `TIMEOUT`、C04 应 `REJECTED`

## 2. `case.fault` 未生效（几行）

**现状**：C03/C04 案例里写着 `fault=timeout / bad_json`，但链路 0.4 秒照常返回正常结果。

**原实现位置**：`inner/service.pyc` → `handle_case(case_id, emp_id, session_id, note, emp, case)`
入参里有 `case`，但没有按 `case["fault"]` 切换行为。

**改成什么**：读案例后，若 `case.get("fault")` 非空，直接走第 1 条的降级分支（或真实注入故障：让模型调用 sleep / 返回非 JSON）。

**验收**：同上，C03/C04。

## 3. 隐私判据缺失（约 20 行，评委最容易试的一条）

**现状**：C01 备注里塞了完整身份证号 + 全卡号，照样 `RESTORED / SHOW_SUGGESTION`，无告警、无阻断。

**原实现位置**：`inner/privacy.pyc`（只有令牌化与解映射：正则 `\b(?:NAME|CARD|PHONE|ID|AMT|DATE|MERCHANT|ACCT|TXN)_\d{3,}\b`）
和 `inner/rules.pyc`（只有 8 条业务规则 + 话术，没有隐私判据）。

**建议的三级判据**（v2 已实现，可直接抄）：

| 级别 | 触发条件 | 处置 |
|---|---|---|
| T1 | 文本命中 18 位证件号；或**备注里**出现完整卡号 | `status=BLOCKED` + 转人工 + 禁复原 + 审计 `PRIVACY_*` |
| T2 | 要求「回拨/回访」且给了完整手机号 | `HUMAN_HANDOFF`（外呼需二次授权） |
| T3 | 其他 | 正常 |

> 注意：A 组案例本身含合成卡号与手机号，**不要**用"出现卡号就阻断"的粗规则，否则 A 组全挂。
> 我们用的区分是「备注里人工粘贴的原始标识」和「业务库按权限取的字段」。

**参考实现**：`v2重写版/app.py` 的 `privacy_judge()`

**验收**：C01 应 `BLOCKED`、C02 应 `HUMAN_HANDOFF`，A01–A04 仍 `SHOW_SUGGESTION`。

## 4. 客户通道与坐席通道判定不一致（半天）

**现状**：同一类问题，坐席端 A01 给建议，客户页 A1/A4 却 `PENDING_HUMAN`（2/2 误转）。

**原实现位置**：`outer/app.pyc` 的反馈提交路径（`fb_submit`）与 `dmz/app.pyc` 的转发，各自有判定逻辑，没有复用 `inner` 的规则裁决。

**改成什么**：客户通道只做「取文本 → 调内网同一裁决入口 → 按结果生成回复」，不要在交换区/外网区各写一套。

**验收**：客户页提「想对一笔 268 元消费提争议，需要准备什么材料」→ 应直接给出办理路径（状态 `AI_ANSWERED`），不是「已转接人工」。

## 5. 并发崩溃（2–3 天，根因项）

**现状**：坐席端 5 并发，15 单全失败、进程静默退出（三个日志都没有异常栈）。1–3 并发正常。

**根因**：单进程三区共用同一个事件循环，模型调用是阻塞式的；并发一上来把主线程憋死，端口不再 accept。

**两条路**：
- **A（推荐）** 改异步：模型调用换 `httpx.AsyncClient` + `asyncio.gather` 限流（信号量 2–4），保持单进程也能扛。
- **B（保守）** 加进程内串行锁：裁决链路一次只处理一个请求，其余排队。

> 我们外挂了一个「串行自愈网关」（`tools/serial_proxy.py`）先把并发变排队：5 并发 15/15、10 并发 20/20，但那是外部兜底，治不了根。

**验收**：
```bash
python tools/wb_loadtest.py --base http://127.0.0.1:<端口> --path case --n 15 --c 5
python tools/wb_loadtest.py --base http://127.0.0.1:<端口> --path case --n 20 --c 10
```
要求成功率 ≥99%、进程不退出。

## 6. 时间口径（几行）

**现状**：工单号内嵌 UTC 时分（`FB20261119**0341**`），页面显示 11:41，差 8 小时。

**原实现位置**：`inner/service.pyc` 的 `_now/_iso/_iso_ms`（时间工具）与工单号生成处。

**改成什么**：统一用本地时区（`datetime.now().astimezone()`），工单号里的时分同步。

**前端配套**：我们已加 `fmtTs()` 按浏览器本地时区渲染，位置在 `h5/index.html`、`web/index.html`、`web/admin.html`，你可以保留。
