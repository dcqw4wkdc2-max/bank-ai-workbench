# 网络隔离方案（T12 不适用 → 怎么补成可验证）

## 一、现在为什么验不了

客户端是**单进程三端口**：内网 8101 / 交换区 8102 / 外网 8103 跑在同一个 Python 进程的不同线程里。
三者之间的"隔离"是**代码约定**（外网区路由表里没有内网接口），不是网络策略。
所以 T12（外网服务直连内网库 → 网络层拒绝）无法构造：物理上它们就是同一个进程。

## 二、补成可验证的三网络形态（需源码，约半天）

```
docker network create bank-inner     # 内网，仅 inner + dmz 加入
docker network create bank-dmz       # 交换区，仅 dmz + outer 加入
docker network create bank-outer     # 外网，仅 outer 加入（可出网）
```
| 容器 | 加入网络 | 暴露端口 | 说明 |
|---|---|---|---|
| inner-app | bank-inner | 内部 8101（不映射到宿主） | 持原始数据、规则、复原、审计 |
| dmz-gateway | bank-inner + bank-dmz | 内部 8102 | 唯一跨域通路，白名单+扫描 |
| outer-app | bank-dmz + bank-outer | 宿主 8103 | 客户入口 + 模型出口 |

### 验证脚本（可以直接放进验收）
```bash
# 1) 外网容器能不能直连内网库？（必须失败）
docker exec outer-app curl -s --max-time 3 http://inner-app:8101/internal/api/v1/health || echo "拒绝 ✅"
# 2) 外网容器能不能绕过网关直连内网 IP？（必须失败）
docker run --rm --network bank-outer curlimages/curl -s --max-time 3 http://inner-app:8101/ || echo "拒绝 ✅"
# 3) 只有网关这一条通路（必须成功）
docker exec dmz-gateway curl -s http://inner-app:8101/internal/api/v1/health
```
三条命令跑完，T12 从"不适用"变"通过"。

## 三、没有源码时的替代做法（现在就能用，但只能算部分）
在单进程形态下，我们已有的事实是：
- 外网区（8103）路由表只有 11 条，**没有任何一条能读内网库**；
- 所有跨域动作都走交换区（8102）的 7 条路由，且带白名单；
- 复原服务只在内网（8101）开放，外网拿不到。

这能证明"**逻辑上是唯一通路**"，但不能证明"**网络层不可达**"。汇报时按这个口径说，别把逻辑隔离说成网络隔离。
